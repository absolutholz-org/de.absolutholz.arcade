# Architecture Decision Records (ADRs)

This document contains the foundational architectural decisions for the Arcade Web App. All automated agents and developers must strictly adhere to these constraints.

## ADR 001: Monorepo Topology and Domain Model

- **Context:** Structuring the codebase to reflect independent products while maximizing code reuse.
- **Decision:** Implement a workspace model (e.g., pnpm workspaces) strictly divided into `apps/` and `libraries/`.
    - `apps/*` are standalone, deployable, user-facing products (e.g., `/hub`, `/sudoku`, `/minesweeper`). Apps do _not_ import each other.
    - `libraries/*` contain all shared business logic, UI components, offline storage wrappers, and localization strings.
- **Constraint:** Apps consume libraries at build time.

## ADR 002: Build Tools and Static Output Generation

- **Context:** The target production servers (Apache/Nginx) do not support Node.js.
- **Decision:** All applications must be built to output purely static assets (HTML, CSS, JS, media).
    - `apps/hub` will utilize Astro to generate pre-rendered, lightweight static pages.
    - Games within `apps/*` will utilize either Vite (for pure React SPAs) or Astro (if they require their own pre-rendered static instruction pages alongside the React game canvas).
- **Constraint:** Server-Side Rendering (SSR) API routes and Node.js middleware are strictly forbidden.

## ADR 003: Application Stitching and Server Routing

- **Context:** Creating a seamless user experience across independent apps on a static server targeting the domain `arcade.absolutholz.de`.
- **Decision:** Applications will be stitched together via directory structure and server-level routing.
    - The CI/CD pipeline will deploy the Hub to the server root (`/`) and games to dedicated subdirectories (e.g., `/sudoku`).
    - Dedicated game subdomains (e.g., `minesweeper.absolutholz.de`) will strictly 301 redirect to the base domain path (`arcade.absolutholz.de/minesweeper`) for SEO and service worker scoping benefits.

## ADR 004: Unified Progressive Web App (PWA) Architecture

- **Context:** Delivering a cohesive offline-capable experience across independent applications.
- **Decision:** A single `manifest.json` and a single master Service Worker will be generated by `apps/hub` and deployed at the domain root (scope `/`).
- **Constraint:** The Service Worker will manage caching strategies for all downstream game directories, caching the static Hub HTML globally, and utilizing a runtime caching strategy (e.g., StaleWhileRevalidate) for game-specific assets only after they are visited.

## ADR 005: Progressive Enhancement and Native Routing

- **Context:** Ensuring baseline usability and adhering to web standards.
- **Decision:** Standard native HTML elements must be used wherever possible. Navigation within and between the Hub's static pages must use standard `<a href="…">` anchor tags, avoiding heavy JavaScript client-side routers for simple page transitions.

## ADR 006: Accessibility Standard (WCAG 2.2 Level AA)

- **Context:** Guaranteeing inclusivity for all users and complying with modern accessibility laws.
- **Decision:** The entire ecosystem must adhere strictly to WCAG 2.2 Level AA.
    - All interactive elements must meet the 24x24 CSS pixel target size minimum.
    - Focus states must be explicitly managed and never obscured.
    - Dynamic game states must utilize ARIA live regions for screen readers.
    - Automated `axe-core` checks must be integrated into the development environment.

## ADR 007: Core Localization (i18n) Strategy

- **Context:** Supporting multiple languages across isolated applications.
- **Decision:** Localization will be implemented natively from day one. Dictionaries and language-detection logic will reside in `libraries/i18n` and be consumed by all `apps/`.
- **Constraint:** Zero hardcoded UI strings are permitted in application code or the component library.

## ADR 008: State Management and Backend Abstraction

- **Context:** Planning for future features (achievements, user accounts, multiplayer) without blocking Phase 1 static deployment.
- **Decision:** All state persistence, user authentication, and multiplayer logic will be abstracted into dedicated packages (`libraries/auth`, `libraries/storage`, `libraries/multiplayer`).
    - For Phase 1, these libraries will export mock data or rely entirely on `localStorage`/`IndexedDB`.
    - Interface contracts must be designed asynchronously so they can be seamlessly replaced with real database/Firebase and WebRTC connections later.

## ADR 009: Shared Dependency Resolution (No Module Federation)

- **Context:** Sharing React and UI components efficiently without overcomplicating the build.
- **Decision:** Shared code will be resolved at build-time via the monorepo workspace. The framework bundlers (Astro/Vite) will naturally extract shared dependencies into optimized chunks. Webpack/Vite Module Federation is explicitly rejected to maintain architectural simplicity.

## ADR 010: CI/CD Pipeline and Browser Support Matrix

- **Context:** Automating deployment and enforcing quality control across specific browser environments.
- **Decision:** Deployment will be handled via GitHub Actions to deploy to the target server directory structure.
- **Constraint:** The development and testing matrix will target the **last 10 versions of Chrome** (Desktop/Android) for the initial Phase 1 build. Cross-browser targets (Firefox, Safari, Edge, Opera, Samsung Internet) will be integrated in subsequent phases prior to production release.

## ADR 011: CSS Architecture and Theming

- **Context:** Delivering a consistent UI with support for user preferences (dark mode) and strict accessibility needs (high contrast), while sharing styles across independent apps.
- **Decision:** All styling and theming will be driven by CSS Custom Properties (Variables) declared at the `:root` level, utilizing `oklch` color spaces and the `light-dark()` function.
- **Constraint:** High Contrast mode overrides (`@media (prefers-contrast: more)`) will be algorithmically generated based on these `oklch` variables in a later phase to prevent CSS bloat in the initial page load.

## ADR 012: Local Storage and State Namespacing

- **Context:** Because all apps are stitched together under `arcade.absolutholz.de`, they share the same browser storage origin.
- **Decision:** All client-side storage keys must be strictly namespaced using the format `arcade::[app-name]::[key]`.
- **Constraint:** Games must never write directly to raw keys (like `highScore`). The `libraries/storage` package should enforce this namespacing format programmatically to prevent data collision between games.

## ADR 013: Package Naming Conventions

- **Context:** A multi-app monorepo requires predictable package resolution to avoid import confusion during build processes.
- **Decision:** All `package.json` names within the workspace must utilize the `@arcade/` scope and denote their topology location.
- **Constraint:** Apps must be named `@arcade/[app-name]` (e.g., `@arcade/hub`, `@arcade/minesweeper`). Libraries must be named `@arcade/lib-[name]` (e.g., `@arcade/lib-ui`, `@arcade/lib-storage`).

## ADR 014: Styling Engine (Vanilla Extract)

- **Context:** We require a type-safe, TypeScript-driven styling developer experience that strictly outputs static CSS at build-time to adhere to ADR 002.
- **Decision:** We will use **Vanilla Extract** (`@vanilla-extract/css`) as the styling engine across the monorepo.
- **Constraint:** Runtime CSS-in-JS libraries (like Emotion or styled-components) are strictly forbidden to eliminate JavaScript runtime overhead for styles in the final production bundles.

## ADR 015: Dependency Version Syncing via pnpm Catalogs

- **Context:** Preventing bugs and bundle duplication caused by multiple versions of core libraries (React, Astro, Vanilla Extract) scattered across different apps and packages.
- **Decision:** We will utilize **pnpm Catalogs** (introduced in pnpm v9.5+) to manage shared dependency versions centrally.
- **Constraint:** Apps and libraries must declare shared dependencies using the catalog reference (e.g., `"react": "catalog:"`) in their `package.json`, rather than hardcoding version numbers. The actual version numbers are defined exclusively in `pnpm-workspace.yaml`.
